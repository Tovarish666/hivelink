# e3372-driver

Драйвер парка USB-модемов **Huawei E3372 / E3131 / E353 и Vodafone K5150-K5160**
на хосте **Proxmox VE / Debian**. Ставится одной командой, дальше работает сам:
доводит модемы до рабочего режима, раздаёт им маршруты, поднимает передачу
данных и чинит всё это при каждом сбое — без участия человека.

Рассчитан на **десятки модемов на дереве USB-хабов**, где заезд занимает минуты,
половина устройств садится не в тот режим, а часть отваливается и возвращается.

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Tovarish666/hivelink/main/install.sh)
```

Идемпотентно, root, Debian 12/13 · Proxmox VE 8/9 · amd64.

---

## Что это делает

Модем E3372 проходит до рабочего состояния четыре развилки, и на каждой умеет застрять:

| Развилка | Как выглядит поломка | Что делает драйвер |
|---|---|---|
| **1. Zero-CD** | `12d1:1f01` — устройство отдаётся как CD-ROM | конфигурация 1, затем `usb_modeswitch` с `HuaweiNewMode`, при отказе — пере-enumeration |
| **2. USB-конфигурация** | `wwanN`, NOARP, DOWN, адреса нет | перебор `bConfigurationValue` до конфигурации, дающей `rndis_host`/`cdc_ether` |
| **3. Передача данных** | интерфейс с адресом, web-API отвечает, наружу трафик не идёт | сессия HiLink → `dataswitch=1`, при `ConnectionStatus != 901` — дозвон |
| **4. Скорость приёма** | всё работает, но download ~1.3 Мбит при нормальном upload | DKMS-патч `rndis_host`: настоящий `rx_urb_size` вместо зашитых 2048 |

Плюс постоянный фон: DHCP, policy routing на каждый модем, уборка осиротевших
правил, защита резолвинга хоста.

**Реакция мгновенная.** udev дёргает драйвер на каждое появление Huawei-устройства,
таймер на 15 с добирает всё, что не сопровождается событием. Как только что-то
на шине стабилизировалось — драйвер уже отработал по нему.

## Развилка 2 подробно — то, из-за чего «половина модемов не поднялась»

HiLink-прошивка отдаёт **несколько USB-конфигураций**. Одна несёт RNDIS/CDC-ECM —
её берут `rndis_host`/`cdc_ether`, появляется `ethN`, работает DHCP и web-API на
`192.168.N.1`. Другая несёт NCM — её берёт `huawei_cdc_ncm`, появляется `wwanN`
с флагом NOARP, raw-IP, без DHCP-сервера на той стороне и без web-API.

Какую взять, решает ядро (`usb_choose_configuration`). При массовом включении оно
регулярно промахивается, и **это состояние стабильное — само не разойдётся**.
Отсюда классическая картина: подождал десять минут, ничего не изменилось; передёрнул
скрипт — заработало (потому что устройства пере-enumerate'нулись и на этот раз повезло).

Драйвер не полагается на везение. Он перебирает конфигурации, запоминает какой
драйвер даёт каждая, и садится на нужную. Результат сохраняется в
`/var/lib/e3372/confmap` по ключу `idProduct:bcdDevice`, поэтому **после первого
раза одинаковые модемы правятся сразу, без перебора** — в том числе после
перезагрузки и на новых экземплярах той же партии.

Целевой драйвер задаётся в конфиге (`PREFER_DRIVER`, по умолчанию `rndis_host`).
Если у модели RNDIS-конфигурации нет вообще, драйвер садится на `cdc_ether` и
пишет об этом один раз в журнал, а не долбится в цикле.

Это прямой аналог того, что виндовый стек Huawei делает через `AT^PORTSEL`, —
выбор композиции интерфейсов.

## Ошибки, которые учтены заранее

Список не гипотетический: всё ниже либо ловилось на живом парке, либо является
известным поведением ядра/systemd, на которое эта конструкция натыкается.

### USB и шина

| Ошибка | Решение |
|---|---|
| Ядро выбрало NCM-конфигурацию → `wwanN` без DHCP | перебор `bConfigurationValue`, запоминание удачной по модели |
| Запись `bConfigurationValue` отбита с EBUSY | сначала `-1` (расконфигурировать), потом целевое значение |
| Zero-CD оказался на конфигурации с MBIM | там нет mass-storage endpoint, `usb_modeswitch` бессилен — сначала ставится конфигурация 1 |
| Модем в Zero-CD не реагирует на `usb_modeswitch` | после `ZEROCD_MAX_TRIES` — `authorized` 0→1, полное пере-enumeration |
| Устройство ещё не привязало драйвер, а мы уже дёргаем конфигурацию | `NODRV_GRACE` циклов ожидания, только потом переход к следующей |
| Конфигурация вообще без сетевой функции (serial-only) | помечается `none`, перебор идёт дальше, а не встаёт |
| Бесконечный перебор конфигураций | счётчики попыток на порт, потолок `CFG_MAX_TRIES`, затем посадка на лучшую известную |
| Бесконечный цикл re-enumerate | счётчик сбрасывается только при успехе, между попытками — полный цикл |
| Устройство исчезло в середине прохода | все чтения sysfs через `-r`/`-d`, отсутствие файла = пропуск |
| `devnum` меняется при каждом пере-enumeration | состояние ключуется **путём USB-порта** (`3-1.4.2.1`), а не номером устройства |
| Автосуспенд усыпил хаб → отвалилась вся ветка | `power/control=on` для модемов и типовых хабов (udev + проход драйвера) |
| Шторм udev-событий при включении 40 модемов | `--no-block` в правиле + `flock` в скрипте: события схлопываются в одну очередь |
| systemd убил юнит по start-limit | `StartLimitIntervalSec=0` в сервисе |
| Проход не уложился в интервал таймера | `flock -n` — новый цикл просто пропускается |

### Сеть

| Ошибка | Решение |
|---|---|
| У всех E3372 одинаковый MAC → матч по имени/MAC невозможен | `.network` матчится **по драйверу** |
| Одинаковый MAC → systemd переименовывает только первый в `enx…`, остальные остаются `ethN` | так и задумано, привязка идёт по подсети `N`, а не по имени |
| Модем прописывает свой DNS и ломает резолвинг хоста | `UseDNS=no`, `UseDomains=no`, `DNS=`, `DNSDefaultRoute=no` |
| `resolv.conf` остался вообще без `nameserver` | снимок при установке + фолбэк в каждом цикле (симлинки resolved не трогаются) |
| Сорок default route дерутся с маршрутом хоста | `UseGateway=false`, `UseRoutes=false`; маршруты только в своих таблицах |
| `N` попал в 253/254/255 → снесли бы таблицы `default`/`main`/`local` | номер таблицы уводится в `10000+N` |
| Дубли `ip rule` копятся при каждом hotplug | `rule_ensure` проверяет точное совпадение, лишние удаляет |
| Правила остались от модема, которого больше нет | сборка мусора в каждом цикле: нет адреса — нет правила, таблица чистится |
| Два модема настроены на одну подсеть | обслуживается первый, второй помечается в журнал (нужна перенастройка модема) |
| strict `rp_filter` ест ответный трафик при policy routing | `rp_filter=2` |
| «neighbour table overflow» на сорока подсетях | подняты `gc_thresh1/2/3` |
| ARP-путаница из-за одинаковых MAC | `arp_ignore=1`, `arp_announce=2` |
| `networkd-dispatcher` не срабатывает: `operstate` остаётся `UNKNOWN`, событие `routable` не приходит | зависимость выброшена, маршруты раскладываются самим драйвером безусловно |
| Интерфейс поднялся, DHCP не доехал | `networkctl reconfigure` с потолком `DHCP_MAX_TRIES` |
| Загрузка хоста ждёт сорок интерфейсов | `RequiredForOnline=no` |

### HiLink web-API

| Ошибка | Решение |
|---|---|
| API отдаёт `<error><code>125002</code>` вместо статуса | сессия: `SesTokInfo` → `Cookie: SessionID` + `__RequestVerificationToken` |
| «Сеть нашёл, но не подключился» — `dataswitch=0` | `AUTO_DATASWITCH`: включается автоматически |
| `ConnectionStatus` 902/904/905/906 | `AUTO_RECONNECT`: дозвон с выдержкой `RECONNECT_COOLDOWN`, без долбёжки |
| Нет регистрации в сети (SIM, сигнал, APN) | распознаётся отдельно, в журнал раз в `QUIET_REPEAT`, дозвон не спамится |
| 40 модемов × HTTP каждые 15 с — лишняя нагрузка | web-API опрашивается раз в `HILINK_EVERY` циклов, параллельно с лимитом |
| Веб-морда модема зависла | таймауты на каждом `curl` |
| Журнал забит одинаковыми сообщениями от 40 устройств | `log_once` с окном `QUIET_REPEAT` |

### Установка и эксплуатация

| Ошибка | Решение |
|---|---|
| Нет `usb_modeswitch` / `curl` / `ethtool` | установка не падает, соответствующий шаг отключается сам и пишет предупреждение |
| Повторная установка затирает пользовательский конфиг | `/etc/e3372/e3372.conf` не перезаписывается, новый кладётся рядом как `.conf.new` |
| Патч ядра установлен на диск, но не загружен в память | `rmmod` не выгружает занятый модуль; перезагрузка повторяется до совпадения значения в `/sys/module` с конфигом |
| Остатки прошлой версии (watchdog, networkd-dispatcher hook, `25-hilink.network`) | снимаются автоматически при установке |
| Прошлые версии клали `usb_modeswitch`-конфиги на `14fe/1505/155a/1c0b` — это switcher-serial PID, не CD-ROM | убираются, оригиналы из `.e3372.bak` возвращаются |
| Сбой одного шага роняет весь проход | `set -e` намеренно не используется в драйвере, каждый шаг изолирован |
| Непонятно, что вообще происходит | `e3372-doctor` — полный дамп одной командой |

## Команды

```bash

e3372-status --no-exit    # то же, но без проверки внешнего IP (быстро)
e3372-status --json       # для панели
e3372-doctor              # полный дамп для разбора
e3372-ctl run             # прогнать цикл прямо сейчас
e3372-ctl dataon --all    # включить мобильные данные везде
e3372-ctl reconnect 115   # пересоединить модем N=115

e3372-ctl recfg --all     # забыть выученные конфигурации и перебрать заново

journalctl -t e3372 -f    # что делает драйвер
```

## Модель адресации

```
модем N:  192.168.N.0/24    сам модем и web-API 192.168.N.1    хост получает 192.168.N.100
```

`N` — единственный стабильный идентификатор модема: он зашит в настройки самого
модема и переживает и переткивание, и перезагрузку, в отличие от имени `ethN`
и от номера USB-устройства. Физическое гнездо всегда видно в `altname`
(`wwp0s20f0u2u4u3u1`) и в выводе `e3372-doctor`.

Диапазоны меняются в `/etc/e3372/e3372.conf` (`HOST_PREFIX`, `HOST_OCTET`, `GW_OCTET`).

## Границы применимости

- Модемы в **stick-режиме** (PID `1506`, `14fe`, `155b` и родня) HiLink'ом не станут:
  у них другая прошивка. Драйвер их распознаёт, сообщает один раз и не трогает.
  Перепрошивка — вне scope.
- Карта PID построена по INF из оригинального пакета **HUAWEI Drivers 5.05.01.158**
  (2014). PID более поздних ревизий (например E3372h-320) в неё не входят —
  такие устройства классифицируются как `other` и обслуживаются по драйверу,
  что для работы достаточно.
- Смена внешнего IP (реконнект по расписанию, ротация) — задача уровня выше,
  [modlink-linux](https://github.com/Tovarish666/modlink-linux), а не этого слоя.
- `systemd-networkd` работает **параллельно** с `ifupdown2` Proxmox: `.network`
  матчит только модемы по драйверу, `enp*`/`vmbr*` не трогает.

## Откуда взялись константы

PID-карта, набор Zero-CD PID и таблица `Prot → функция порта` извлечены из
INF-файлов оригинального Windows-пакета Huawei (`FcSwitch.inf`, `ewqsnet.inf`,
`ew_usbenumfilter.inf`, `ew_hwusbdev.inf`, `ew_cdcacm.inf`). Оттуда же —
подтверждение, что переключение Zero-CD это SCSI-команда rewind, а типизация
интерфейсов у самой Huawei идёт по `Subclass/Prot`, а не по номеру интерфейса.

## Развилка 4 подробно — скорость приёма (баг ядра)

Модем поднялся, дозвонился, трафик идёт — но **download ~1.3 Мбит/с при
совершенно нормальном upload**. Тот же модем под Windows выдаёт 50+.

`generic_rndis_bind()` сообщает устройству максимальный размер транзфера,
вычисляя его из `rx_urb_size`:

```c
dev->rx_urb_size = dev->hard_mtu + (dev->maxpacket + 1);
dev->rx_urb_size &= ~(dev->maxpacket - 1);
u.init->max_transfer_size = cpu_to_le32(dev->rx_urb_size);
```

Для High-Speed это `(1558 + 513) & ~511` = **2048 байт**. Модем честно уважает
это число и режет батчи так, что RNDIS-сообщения не помещаются в один URB.
А `rndis_rx_fixup()` собирать сообщение через границу URB не умеет — каждый
буфер разбирается отдельно, и у сообщения, начавшегося в предыдущем URB,
«заголовком» оказывается кусок полезных данных.

Диагностируется по счётчикам: почти весь приём — брак, при этом `crc = 0`
(данные по USB доезжают целыми) и `overrun = 0` (хост успевает их забирать):

```
RX:  packets 20196   errors 17881
RX errors:  length 11084   crc 0   frame 6792   fifo 0   overrun 0
```

При включённой отладке парсера видно прямо:

```
bad rndis message 1/1460/36/1414, len 588
```

Заголовок корректен (`36 + 1414 + 8 <= 1460`), но пришло 588 байт из 1460.

Баг не специфичен для Huawei — та же сигнатура известна на Samsung
(Debian #889831), открыт с 2018 и в апстриме не исправлен.

**Решение:** параметр модуля, переопределяющий `rx_urb_size` до того, как
значение уйдёт в `max_transfer_size`. Замерено на живом парке K5160:

```
было   download  1.05 Мбит/с   upload  9.69   ошибок приёма ~85%
стало  download ~50 Мбит/с     upload ~55     ошибок приёма ~15%
```

Оформлено DKMS-пакетом `e3372-rndis-fix`: `DEST_MODULE_LOCATION=/updates`
перекрывает штатный модуль, `AUTOINSTALL=yes` пересобирает его на обновлении
ядра. Размер задаётся `RX_URB_SIZE` в конфиге, `0` полностью отключает фикс.

Failure mode безопасный: если конфиг потеряется, параметр станет `0` и драйвер
вернётся к штатному поведению — медленно, но рабоче. Если апстрим перепишет
`generic_rndis_bind()`, сборка упадёт с понятной ошибкой, а не наложит кривой
патч; парк при этом продолжит работать. Отключить целиком:
`SKIP_RNDIS_FIX=1 bash install.sh`.

Проверить, что активен исправленный модуль:

```bash
modinfo rndis_host | grep filename      # должно быть .../updates/dkms/rndis_host.ko
cat /sys/module/rndis_host/parameters/rx_urb_size_override
```

### Как убедиться, что фикс действительно работает

Мало проверить, какой файл лежит на диске — важно, что загружено в память:

```bash
modinfo rndis_host | grep filename      # должен быть .../updates/dkms/rndis_host.ko
cat /sys/module/rndis_host/parameters/rx_urb_size_override
```

Если файл пропатченный, а параметра нет — в памяти работает штатный модуль,
и приём будет сыпаться как прежде. Так бывает, когда `rmmod` не смог выгрузить
драйвер, к которому привязаны интерфейсы. `build.sh` это делает правильно:
отвязывает устройства, выгружает, загружает и **повторяет до совпадения**
значения в `/sys/module` с конфигом.

Быстрый признак проблемы — доля брака на приёме:

```bash
ip -s -s link show <интерфейс> | sed -n '/RX:/,/TX errors/p'
```

`crc = 0` и `overrun = 0` при больших `length`/`frame` — это именно этот баг,
а не кабель, питание или радио.

## Полезное при разборе

**`authorized 0→1` не снимает питание.** Он только логически отцепляет
устройство от хоста; модем продолжает работать, и зависшая радиочасть так не
оживает. Настоящая перезагрузка — снятие питания на порту хаба:

```bash
uhubctl -l <хаб> -p <порт> -a off -f && sleep 5 && uhubctl -l <хаб> -p <порт> -a on -f
```

Хабы `1a40:0101` формально объявляют «ganged power switching», но по портам
переключаются. `uhubctl` без `-f` их не признаёт — флаг обязателен.

**Пустой `device/information`** (нет IMEI, модели, ICCID) при отвечающем
веб-сервере означает, что радиоблок не стартовал: у HiLink это отдельный
процессор. `SimState=255` в `monitoring/converged-status` — SIM не обнаружена.

**`e3372-status` на двух десятках модемов** опрашивает их последовательно и
занимает минуты. Для быстрой сводки удобнее свой параллельный обход
(`... &` в цикле и `wait`).
